**Ответ по пункту 3. Нет: сетка волны 12 (cMin 0,1 нм, cMax 1 нм, 150 классов, адаптивная) не искажает результатов 12-1, 12-9 и 13-Б на горизонтах выдачи (200 ч и 87 600 ч) сверх долей процента. Искажена только стадия зарождения — несколько шагов решателя после его начала.** Зародыш крупнее `cMax` kawin 0.5.0 кладёт в последний класс молча, без предупреждения. Но заполненный последний класс сразу же достраивает сетку вверх — на 37 классов за шаг, пока она не накроет зародыш. Закрывает это не адаптивность (`adaptive=True`), а безусловная достройка в `adjustSizeClassesEuler`, которая работает при любом значении флага. Адаптивность только пересобирает сетку, когда классов больше `maxBins`, и этим ускоряет рост верхней границы. Направление искажения на стадии зарождения: зародыши этих шагов записаны мельче `Rnuc`, докритические растворяются, и пересыщение расходуется медленнее. Поэтому доля и средний радиус занижены, а скорость зарождения и число частиц завышены. Порядок величины — из опыта на Ni–9,8Al–8,3Cr (пункт 2, худший случай: `cMax` ниже критического радиуса). Через 0,5 мс после первых зародышей доля ниже на 63 %, число частиц выше на 14 %. На 0,1…0,3 с расхождение около 1 % по числу частиц. К 1 с — 2·10⁻⁵ по доле, 6·10⁻⁴ по радиусу, 2·10⁻⁴ по числу частиц. Для ЭК199 горизонты 200 и 87 600 ч отстоят от первого узла с частицами не меньше чем в 670 раз (в опыте — в 50 раз), так что искажение там не крупнее, и по кэшам затронутые случаи идут вровень с соседями. Это перенос с учебного сплава, прямым счётом на ЭК199 не проверялось.

## 1. Куда kawin 0.5.0 кладёт зародыш крупнее верхней границы сетки

Код — `.venv-windows/Lib/site-packages/kawin/precipitation/` основного клона, kawin 0.5.0
(`kawin-0.5.0.dist-info/METADATA`: `Version: 0.5.0`). SHA-256 файлов:
`PopulationBalance.py` `2e185e61…d37884`, `KWNEuler.py` `1205bfc0…3b5ae9`, `KWNBase.py`
`3507e6f6…9b3801`. `PopulationBalance.py` в `ThermoGar-Installer-Assets/runtime-clean-3119`
побайтово тот же (`cmp`), то есть у установленного приложения механизм тот же.

**Ответ.** Сетка не обрезает радиус и не отказывает, предупреждения не выдаёт. Зародыш молча
попадает в **последний класс** текущей сетки. Затем, если в этом классе оказалось больше одной
частицы на м³, сетка **расширяется вверх** на `int(originalBins/4)` классов той же ширины
(37 при 150 классах). Если классов стало больше `maxBins`, а адаптивность включена, сетка
пересобирается на `minBins` классов в тех же границах. В следующем шаге зародыш снова идёт в
последний класс, пока верхняя граница не перейдёт `Rnuc`. Ни в `PopulationBalance.py`, ни в
`KWNEuler.py`, ни в `KWNBase.py` нет `warnings` или `logging`: `grep` по `import warnings`,
`warnings.warn` и `logging` пуст.

**Шаг 1 — выбор класса.** `PopulationBalance.py`, строки 551–554 (`getdXdtEuler`), и то же в
строках 598–601 (`correctdXdtEuler`):

```python
        #Find size class for nucleated particles
        nRad = np.argmax(self.PSDbounds > nucRadius) - 1
        dXdt[nRad] += nucRate
```

Если `nucRadius` больше последней границы `PSDbounds[-1]`, массив `PSDbounds > nucRadius` весь из
`False`. `np.argmax` от массива без единого `True` возвращает 0, значит `nRad = -1`, и
`dXdt[-1]` — последний класс по отрицательному индексу Python. Частица записана с радиусом центра
последнего класса. У начальной сетки волны 12 это `1 − 0,006/2 = 0,997` нм. Тот же `-1` получается,
когда зародыш меньше `cMin` (все `True`, `argmax` = 0): этот случай BL-22 уже ловит, и docstring
`_check_size_grid` его описывает.

**Шаг 2 — отсев меньше одной частицы.** `PopulationBalance.py`, строки 616–617 (`updatePBMEuler`):

```python
        self.PSD = newN
        self.PSD[self.PSD < 1] = 0
```

**Шаг 3 — достройка сетки.** `KWNEuler.py`, строки 630–631 (`_updateParticleSizeDistribution`),
сразу после обновления:

```python
            self.PBM[p].updatePBMEuler(t, x[p])
            change, addedIndices = self.PBM[p].adjustSizeClassesEuler(all(self.growth[p] < 0))
```

`PopulationBalance.py`, строки 412–431 (`adjustSizeClassesEuler`):

```python
        change = False
        newIndices = None
        if self.PSD[-1] > 1:
            #print('adding bins')
            newIndices = self.bins
            self.addSizeClasses(int(self.originalBins/4))
            change = True

        if self._adaptiveBinSize:
            if self.bins > self.maxBins:
                #print('reducing bins')
                self.changeSizeClasses(self.PSDbounds[0], self.PSDbounds[-1], self.minBins)
                change = True
                newIndices = None
```

`addSizeClasses`, строки 383–388 — граница растёт на число добавленных классов, умноженное на
текущую ширину:

```python
        self.bins += bins
        self.PSD = np.append(self.PSD, np.zeros(bins))

        self.max += bins * (self.PSDbounds[1] - self.PSDbounds[0])
        self.PSDbounds = np.linspace(self.min, self.max, self.bins+1)
```

Проверка `self.PSD[-1] > 1` стоит **вне** `if self._adaptiveBinSize`: достройка работает и при
`adaptive=False`. Сам kawin пишет об этом в docstring `setAdaptiveBinSize` (строка 274): «If False,
the bins will still be if nucleated particles are greater than the max bin size» (в оригинале
пропущено слово — видимо, «added»). Отдельной ветки «зародыш больше границы» в коде нет: это та же
общая достройка «последний класс начал заполняться», что и для растущих частиц.

**Начальная граница.** `PopulationBalance.py`, строка 57: `self.originalMax = np.amax([10*self.originalMin, cMax])`.
При cMin 0,1 нм и cMax 1 нм верхняя граница ровно 1 нм.

**Когда `Rnuc` вообще передаётся.** `KWNBase.py`, строки 455–459:

```python
            dt = t if self.data.n == 0 else self.data.time[self.data.n] - self.data.time[self.data.n-1]
            if nucRate*dt >= self.constraints.minNucleateDensity and Rcrit >= self.precipitates[p].Rmin:
                Rnuc = nucfuncs.nucleationRadius(T, Rcrit, precParams)
            else:
                Rnuc = 0
```

**Что из этого следует.**

* Зародыш крупнее `cMax` в первом шаге записан с радиусом ≤ `cMax`. Если `Rcrit` < `cMax`, частица
  закритическая и растёт; ошибка — только начальный радиус (0,997 против 1,060 нм у случая Д-2,
  объём зародыша занижен в `(0,997/1,060)³ = 0,83` раза).
* Если `cMax` ≤ `Rcrit`, зародыш записан **докритическим**: рост отрицательный, частицы
  растворяются и отдают растворённое обратно в матрицу. Пока живут, они считаются частицами, а
  пересыщение почти не расходуют; как это сдвигает числа — пункт 2.
* После первого же шага, в котором в последнем классе больше одной частицы, граница растёт.
  Для сетки волны 12 это 1,000 → 1,222 → 1,444 нм; на втором расширении классов становится 224 > 200, и
  сетка пересобирается на 100 классов шириной 0,0134 нм; третье расширение даёт ещё +0,497 нм, до
  1,941 нм. Зародыш до 1,9 нм сетка накрывает за три шага зарождения, до 3 нм — примерно за пять.
* Пока в каждом шаге зарождается меньше одной частицы на м³, отсев шага 2 обнуляет её в любом
  классе. Поэтому сетка не расширяется, но и при правильном классе частиц не было бы: исход
  «выделений нет» от сетки не зависит.

## 3. Искажает ли сетка волны 12 результаты 12-1, 12-9 и 13-Б

| γ = 0,150 | 1,520 | частично докритическим (1,12 нм в узле) | 21,5 | 3,57·10²¹ | 34 | 22 |
| γ = 0,175 | 1,753 | докритическим (0,997 нм в узле) | 21,4 | 3,56·10²¹ | 34 | 22 |

При 750 °C границы, γ = 0,150 (докритическая запись на 3,6 с): 18,4 % и 5,65·10²⁰ за 200 ч
— продолжение монотонного спада числа частиц по `γ` у границ зёрен при 750 °C: 2,16·10²¹ →
1,43·10²¹ → 1,05·10²¹ → 5,65·10²⁰ при γ = 0,050…0,150. Равновесная доля за 87 600 ч сеткой не задаётся вовсе: 22 % при 700 °C и
18,7…18,8 % при 750 °C у всех случаев с выделениями.

**BL-23 этим не объясняется.** Оба выпадающих случая BL-23 (700 °C, объём, γ = 0,100; 700 °C,
границы, γ = 0,125) лежат в зоне `Rnuc` > 1 нм. Но случаи 700 °C, границы, γ = 0,150 и 0,175
отстают по сетке сильнее — зародыши записаны докритическими — и огрубляются как соседи. Отставание
сетки не может быть достаточной причиной BL-23. Это вывод из чтения, не диагноз BL-23.

**Случаи «выделений нет».** Там, где число частиц всё время меньше 1 на м³ и зародыш крупнее 1 нм (700 °C: объём γ = 0,150, границы γ = 0,200; 750 °C: объём γ = 0,125;
580 °C: объём γ = 0,175, границы γ = 0,250; 664 °C: объём γ = 0,150; 595 °C: объём γ = 0,175),
средний радиус 0,997 нм стоит в узлах с ненулевым числом частиц: зародыши каждый
шаг идут в последний класс, сетка не растёт. Но по шагу 2 пункта 1 доля меньше одной частицы
обнуляется в любом классе, так что и при правильном классе выделений бы не было. Исход «нет
выделений» — от порога kawin в одну частицу на м³ на шаг, а не от сетки.

**Чего чтение не устанавливает.** В кэшах ряды пишутся по узлам с 3,6 с, а не по шагам решателя.
Сколько шагов зародыши ЭК199 шли мимо своего класса и насколько при этом сдвинулись доля, радиус и
число частиц на стадии зарождения, по ним не посчитать. Порядок величины взят из пункта 2: на
горизонте, в 50 раз дальше начала зарождения, расхождение 10⁻⁵…10⁻³. У 12-1, 12-9, 12-9б и 13-Б
горизонт 200 ч отстоит от первого узла с частицами (0,001…0,298 ч) не меньше чем в 670 раз. Это
перенос, а не замер: состав, число компонентов и шаги решателя у ЭК199 другие.

## 4. Нужна ли третья проверка в `_check_size_grid`

**Вывод: нужна, но как предупреждение, а не отказ.** В код ничего не внесено, решение за мастером.

Почему нужна. Зародыш вне начальной сетки kawin обрабатывает молча, а стадия зарождения при этом
искажена заметно: в опыте −63 % доли и +15 % пика скорости зарождения. Эту стадию пользователь
видит на графиках кинетики с логарифмической осью времени, а признак ошибки — ступенчатый
средний радиус в первых строках кинетики — ему не заметен. Исправить сетку просто: поднять
«Начальный максимальный радиус».

Почему не отказ. Два нынешних отказа BL-22 стоят на грубых ошибках: ложная доля до 100 %
(широкий класс) и зародыш ниже `cMin`, который уходит в последний класс *выше себя* и завышает
объём. Здесь kawin сам достраивает сетку, и итоговые числа сдвигаются в четвёртом-пятом знаке —
меньше, чем от ширины класса на сетке, которую проверка пропускает. Кроме того, `Rnuc` растёт с
`γ`, и дальше всего за `cMax` выходят случаи, где зарождения нет вовсе (у 12-1: `Rnuc` 4,8 и
6,0 нм при γ = 0,5). Отказ запретил бы честный ответ «выделений нет» при больших `γ`.

Как устроить, если мастер согласится:

* та же оценка `_nucleus_estimates` до расчёта, но **наибольший** `Rnuc` по температурам профиля, а
  не наименьший, как в проверке `cMin`: при нагреве зародыш крупнее, а сетка к этому шагу может
  быть не достроена, если частиц ещё нет;
* сообщение — в `PrecipitationResult.warnings`: приложение уже выводит их через `st.warning`
  (`app/thermogar_precipitation.py`, строки 1318–1319); расчёт не останавливается;
* **не** делать парную проверку после расчёта по всем шагам против начального `cMax`, как у двух
  нынешних строк `kwn_quality`. `Rnuc` растёт по мере обеднения матрицы (в варианте B — с 1,024 до
  1,981 нм за 1 с), а сетка растёт вместе с частицами, так что такая проверка срабатывала бы на
  годной сетке. После расчёта честно проверить можно только шаги до первой достройки сетки, а
  границ сетки по шагам приложение не хранит (`setPSDrecording(False)`).

Предлагаемый текст:

```
Радиус зародыша {rnuc_nm:.3g} нм (оценка при {temperature_c:.1f} °C по начальному составу) больше
начального максимального радиуса сетки {cmax_nm:.3g} нм. kawin записывает первые зародыши в
последний класс сетки, мельче их настоящего размера, и достраивает сетку вверх, пока она не
накроет зародыш; на это уходит несколько шагов расчёта. Итоговые доля, радиус и число частиц от
этого почти не меняются, но начало зарождения на графиках искажено: доля и радиус занижены,
число частиц завышено. Чтобы этого не было, задайте «Начальный максимальный радиус» больше
{rnuc_nm:.3g} нм.
```

Если мастер выберет отказ, фразу «Итоговые доля, радиус и число частиц от этого почти не
меняются, но…» надо убрать, а последнее предложение заменить на «Увеличьте «Начальный
максимальный радиус» выше {rnuc_nm:.3g} нм».
